# Объём сборки Swift-версии под Playgrounds

## Суть
Playgrounds на iPad собирает приложение отладочной сборкой целиком внутри себя. Когда сгенерированного кода слишком
много, сборка падает с «Build failed» без ошибок в списке, iPad греется; около порога — «со второго раза».
Это не выражение-«бомба»: проверка типов в проекте быстрая (самое медленное тело — ~0,3–0,5 с).

Ориентир — **число инструкций IR** сборки всего модуля под iPad (arm64), строка CALIBRATION:

| коммит | инструкций IR | на iPad |
|---|---:|---|
| 114cca4 | 1,51 млн | надёжно |
| 8a12490 | 1,93 млн | с первого раза |
| 166c360 | 1,903 млн | 54979d2 — с первого, 5bff89e — со второго |
| 1d309b1 | 1,912 млн | с первого раза |
| c243b18 | 1,912 млн | со второго раза (порог плавает) |
| 45b548d | 1,946 млн | с первого раза |
| 37fa635 | 1,947 млн | с третьего раза |
| 1a15c2a | 1,958 млн | со второго раза |
| 1f2950b | 1,99 млн | со второго раза |
| 4b3a968 | 2,03 млн | не собиралась |

Держать **не выше ~1,85 млн** (на 1,91 — то с первого, то со второго раза: порог плавает от состояния iPad). Пиковая память на Mac (MaxMallocUsage ~1,57–1,59 ГБ) правок не показывает —
по ней не судить. UI на Linux не собирается — единственная проверка компиляции UI до iPad — этот замер в Xcode.

## Как замерить
1. Замер — по необходимости (решение пользователя): крупные правки интерфейса, сборка снова не с первого раза или
   просьба пользователя. Закоммитить правку в ветку `swift`, в сообщении коммита — метка `[calibrate]`; запушить.
   Архив для iPad после замера — только если сборка без ошибок.
2. Workflow `.github/workflows/swift-build-profile.yml`, задача `calibrate (HEAD)` (~3 мин, macOS, Xcode 26).
   Без метки задачи пропускаются (минуты Actions не тратятся); `[profile]` — полный профиль: время проверки
   типов по функциям и выражениям, память и объём IR по файлам (скрипты `ios/tools/build-profile-report.py`,
   `ios/tools/build-stats-report.py`).
3. Читать лог задачи через GitHub MCP (`actions_list` → `list_workflow_jobs`, `get_job_logs` с `tail_lines` ~165):
   - `CALIBRATION HEAD: memory … MB, IR insts N, IR functions …` — главное число N;
   - `error:` / `BUILD FAILED` в шаге сборки — ошибка компиляции UI, исправить до отправки на iPad;
   - `FUNCTIONS total … / TOP FILES` — функции по видам и по файлам (где искать запас).
   Артефакт из облачной сессии не скачать (хранилище закрыто сетью) — всё нужное печатается в лог.
4. Сравнить с таблицей. Выше ~1,94 млн — облегчить до отправки на iPad.
5. Проверка на iPad (пользователь): перезагрузить iPad, App Preview не открывать, ▶; результат — с первого раза,
   со второго или «Build failed». Архив — `git archive --format=zip --prefix=JAMbo-swift/ origin/swift` в чат.

## Чем облегчать (что сработало, по выгоде)
- **Меню и формы — списком, а не отдельной кнопкой в коде.** Ряды кнопок — `MenuChoice` + `MenuChoiceRow` /
  `MenuChoiceButtons` / `MenuChoiceColumn` (UI/PatternMenus.swift); формы (подпись, пояснение, ряд кнопок,
  рычажок, свой вид) — `FormRows` (UI/FormRows.swift: `.head`, `.label`, `.note`, `.choices`, `.toggle`, `.view`).
  EXPORT SONG так — −23 тыс. инструкций.
- **Большие ветки `if` / `switch` видов — `AnyView` в каждой ветке** (функция возвращает `AnyView`): центр экрана
  (RootView.center, `WithMeter`, `MainCenter`) — −22 тыс.; вкладки SETTINGS, меню аранжировщика, MIDI, мастера.
  Скрипт-образец для `@ViewBuilder`-switch: каждая ветка `return AnyView(...)`.
- **Длинная цепочка модификаторов (alert, onChange, fileMover…) — содержимое в отдельном свойстве, тело —
  `AnyView(содержимое)` и цепочка** (EqView `eqMain`, LibraryBrowser `libMain`, ProjectsMenu `projectsMain`).
- Убрали `@ViewBuilder` у функции или свойства — тело должно возвращать значение (`return`), у цепочки `if` без
  `else` — `return AnyView(EmptyView())` в конце; иначе ошибка компиляции (1.11, b6477cc).
- Поведение не меняется: состояние внутри ветки сохраняется (тип ветки тот же), `.id` внутри `AnyView` работает.
  ForEach по индексу в списках — только для строк без своего @State или с временным состоянием.

## Где ещё запас (если понадобится)
- `AppModel` — @Observable: ~10 функций на наблюдаемое свойство (~1,5 тыс. из 2,5 тыс. функций файла).
  `@ObservationIgnored` — только свойствам, которые никакой вид не читает ни прямо, ни через вычисляемые
  свойства (иначе вид перестанет обновляться) — проверять по коду, при сомнении не трогать.
- Крупные файлы по функциям: EqView, PatternGrid, RootView, TopBar, PatternMenus, ArrangeMenus, MasterWindow,
  ArrangeAutoPanel, ArrangeWindow, PagesColumn, SideColumns, ArrangeHeaders.
- Вынос SELF-TEST из приложения (~2 %; решено 1.11 — делать следующим), панда и DIAGNOSTICS (~1 %) — **только по решению пользователя**.

## Чего не делать
- Не ждать от упрощения выражений и проверки типов выигрыша — дело в объёме сгенерированного кода.
- Не менять Package.swift (только через Playgrounds), не добавлять unsafeFlags и модули.
- Не отправлять пользователю на iPad версию без замера, если она добавляет заметный объём UI.
